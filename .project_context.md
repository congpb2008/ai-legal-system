## 1. Project Vision

A production-grade **legal knowledge platform** (concrete product instance branded *"Banking Legal Platform"*
across most product/domain specs; the runtime system is referenced generically as the *"Legal Knowledge Platform"*
in README, contracts, and this context doc — same project, two labels; see §12 finding F1).

It turns uploaded legal / banking documents into a canonical structured representation, performs hybrid
retrieval, and generates **evidence-grounded answers with verifiable, traceable citations**.

What it does:
- Accepts PDF (digital), PDF (scanned, handled by OCR), and DOCX uploads.
- Parses each document into a **Knowledge Tree** — the canonical, immutable representation that preserves
  legal hierarchy (Document → Chapter → Section → Article → Clause → Point / Appendix / Table / Figure /
  Paragraph / Unknown).
- Indexes the tree's derived artifacts (chunks, embeddings, search indexes) for hybrid
  (keyword + semantic) retrieval scoped by vault.
- Generates answers from retrieved evidence only, with citations traceable back to the
  original source file. **Abstains instead of hallucinating** when evidence is insufficient.
- Enforces vault isolation (Personal / Department / Common / Project) and audit logging.

Guiding priorities — never inverted (constraints.md canonical form):
**Accuracy → Traceability → Reliability → Maintainability → Performance.**
Correctness is always preferred over fluency. The platform is a **read-only research
assistant** for decision support; it never provides legal advice and never modifies
documents. A human makes every final legal or business decision (BC-001, BC-002).

Primary content language: **Vietnamese (vi)**; example corpus targets internal banking
regulations (Decision 15/2026/QĐ-NH style — Decisions, Circulars, Decrees, Laws,
internal regulations).

End-to-end traceability chain that must always hold:
```
Answer → Citation → Knowledge Node → Knowledge Tree → Document Version → Original Source File
```

## 2. System Architecture

### Philosophy
> Knowledge flows. Modules transform knowledge. Contracts preserve knowledge.
> Everything else is replaceable. (architecture.md)

A layered, **contract-driven** architecture with one module per responsibility. Modules
communicate **only through Contracts**; higher layers may depend on lower-layer contracts,
**lower layers never depend on higher ones** (e.g., Generation may touch the Retrieval
Contract, never the vector database directly).

### Five logical layers
| Layer | Consumes | Produces | Owns | Does NOT |
|---|---|---|---|---|
| 1. Ingestion | Documents | Knowledge Tree Contract | OCR, parsing, metadata extraction, KT construction, document evolution analysis | retrieval, embeddings, AI answers |
| 2. Knowledge | Knowledge Tree Contract | Knowledge services | persistence, versioning, validation, vault organization | retrieval, LLM, search ranking |
| 3. Retrieval | Query + Knowledge Layer | Retrieval Contract | keyword/semantic/hybrid search, ranking, filtering, vault filtering | generation, document modification |
| 4. Generation | Retrieval Contract | Answer Contract | explanation, comparison, summarization, formatting, citation generation | search, OCR, parsing |
| 5. Presentation | Answer Contract | User Interface | rendering, highlighting, markdown, navigation, upload | business logic |

### Runtime topology (deployment-view.md, physical)
The API Gateway splits **interactive requests** (low-latency, synchronous — ask/search/browse/view-citations)
from **background jobs** (long-running, retryable, observable — OCR/parsing/re-index/re-embed/batch-upload).
- The client never waits for OCR or indexing; it receives a Job ID.
- Query runtime stays synchronous: Gateway → Authentication → Vault Authorization → Retrieval → Generation → Streaming Response → Client.
- Upload runtime is async: Client → Gateway → Store Original → Create Processing Job → return Job ID; Worker runs OCR → Parser → KT → Chunk → Embedding → Index → Completed.
- Priority order: user queries > upload > maintenance/re-indexing/parser migration.
- Multiple jobs and multiple queries run concurrently; avoid global locks.
- Document runtime states: Uploaded → Queued → Processing → Indexing → Ready → Archived → Reprocessing.
- Recoverable failures are retried; unrecoverable failures **halt the pipeline early** (no silent failures).
- Original documents are never modified; failed jobs never corrupt canonical knowledge; every job is traceable.

### Replaceable components (replacement must not require Contract changes)
OCR engine, parser, chunk generator, embedding model, vector database, retrieval
strategy, Large Language Model, keyword/reranking model.

### Architectural invariants (architecture.md)
INV-001 Knowledge Trees immutable; INV-002 every answer originates from retrieval;
INV-003 generation never reads source documents directly; INV-004 retrieval never
generates text; INV-005 presentation performs no business logic; INV-006 derived
artifacts always rebuildable; INV-007 contracts define communication boundaries;
INV-008 the original document remains the ultimate source of truth.

## 3. Processing Pipeline

Two independent pipelines. The document pipeline prepares knowledge (async); the query
pipeline consumes knowledge (sync). They meet **only at the Knowledge Layer** —
knowledge is created once and consumed many times.

### Document Pipeline (knowledge creation)
```
Upload → OCR → Parser → Knowledge Tree → Chunking → Embedding → Index → Ready
```
- Stages 1–4 produce **canonical** data (Original Document → Knowledge Tree). Immutable.
- Stages 5–7 produce **disposable** artifacts: chunks, embeddings, indexes. Rebuildable.
- **Reprocessing** (Re-OCR → Re-Parse → Re-Chunk → Re-Embed → Re-Index) never changes
  Document identity; it produces a new Knowledge Tree while historical versions are kept.
- Failure at any stage stops the pipeline (Upload failure / OCR failure / Parsing failure → Stop).
  Knowledge preservation takes precedence over completion.
- End-to-end observability: every stage records execution time, processing version, warnings, errors.

### Query Pipeline (knowledge consumption)
```
Question → Query Understanding → Retrieval → Evidence Selection → Generation → Citation → Delivery
```
- Query Understanding identifies intent, requested documents, filters, vault scope — **no legal reasoning occurs**.
- Retrieval selects *what is relevant*; Generation selects *how to communicate it*.
- Generation consumes only the Retrieval Contract. It never reads source documents,
  never accesses the vector database, never performs retrieval.
- An **empty evidence list is a valid result**: the system returns `status = NO_EVIDENCE`,
  explains why, and never fabricates content.
- PARTIAL clearly distinguishes confirmed vs. missing information.

### Traceability chain (must hold end-to-end)
```
Answer → Citation → Knowledge Node → Knowledge Tree → Document Version → Original Source File
```

## 4. Module Responsibilities

From `03-architecture/module-specifications.md`. Each module owns exactly one
responsibility, consumes a Contract, produces a Contract, and is independently
testable; a module never accesses another module's internal implementation.

| Module | Consumes | Produces | Owns | Does NOT |
|---|---|---|---|---|
| **Gateway** | HTTP requests | Internal requests | authentication, authorization, routing, request validation, response formatting | OCR, retrieval, generation |
| **Ingestion** | Document Contract | Knowledge Tree Contract | upload, OCR, parsing, metadata extraction, document registration, document evolution analysis | retrieval, embedding search, AI answer |
| **Knowledge** | Knowledge Tree Contract | Knowledge services | persistence, version management, validation, vault organization | retrieval, LLM, search ranking |
| **Chunking** | Knowledge Tree Contract | Chunk Collection | chunk generation, context preservation, source mapping | embedding, search |
| **Embedding** | Chunk Collection | Embedding Collection | embedding generation, embedding versioning | retrieval, ranking, AI generation |
| **Indexing** | Embeddings | Search Index | vector indexing, keyword indexing, metadata indexing | answer questions |
| **Retrieval** | Query + Knowledge Layer | Retrieval Contract | keyword/semantic/hybrid search, ranking, filtering, vault filtering | generate answers, modify documents |
| **Generation** | Retrieval Contract | Answer Contract | explanation, comparison, summarization, formatting | search, OCR, parsing |
| **Citation** | Answer Draft + Evidence | Final Citations | source mapping, legal references, anchor generation | retrieval, generation |
| **Vault** | User identity + Vault metadata | Access Decision | vault isolation, department separation, personal vaults, permission checks | OCR, AI |
| **Observability** | Events | Logs, Metrics, Traces | logging, metrics, audit trail, processing history | business logic |

> **Note on the Reranker (Task 010):** Tasks treat the Reranker as a peer module
> (Retrieval → Reranker → Generation), but `module-specifications.md` does not list it as
> a standalone module and `retrieval-contract.md` lists "reranking metadata" as a future
> Extension Point. This is an open ambiguity — see §12 finding F4. The implementation
> treats Retrieval (recall) and Reranker (precision) as separate tasks.

## 5. Domain Entities & Lifecycle

From `01-domain/domain-model.md` + `01-domain/knowledge-tree-specification.md`.

```
Organization → Vault → Document → Document Version → Knowledge Tree → Knowledge Node →
  Chunk → Embedding → Search Index
Citation → references → Knowledge Node
AI Response = Question + Retrieved Evidence + Generated Answer + Citations + Confidence
```

Lifecycle / ownership chain: Source File owns Document Version owns Knowledge Tree
owns Knowledge Nodes; Knowledge Tree generates Chunks; Chunks generate Embeddings;
Embeddings populate Search Index.

**Immutable (canonical, backed up, versioned, integrity-verified):**
Source File, Document Version, Knowledge Tree, Knowledge Node.
(*ADR-003 additionally includes Metadata Registry as canonical.*)

**Disposable (reproducible, version-tracked, no independent backup):**
OCR Output, Chunk, Embedding, Keyword Index, Vector Index, Retrieval Cache, Temporary Search Results.

Invariants: one Chunk ↔ exactly one Document Version; one Knowledge Node ↔ one Knowledge Tree;
one KT ↔ one Document Version; one Document Version ↔ one Document; one Document ↔ one Vault
+ one Organization + ≥1 Version; Citations reference existing Knowledge Nodes; Embeddings
require Chunks; Search Indexes require Embeddings/Keywords.

Document lifecycle (contract): Created → Active → Archived (never physically deleted by normal ops).
Processing lifecycle (deployment): Uploaded → Queued → Processing → Indexing → Ready → Archived → Reprocessing
(task 001 lists a finer-grained OCR/Parsing state machine). These two state machines are orthogonal but
share the `"status"` field name — see §12 finding F7.

## 6. Contracts

From `02-contracts/`. Four canonical contracts — stable, backward-compatible,
independently versioned. Contract modification requires the developer-guide flow:
**ADR → Contract Update → Examples Update → Implementation Update**. Never invent fields,
remove fields, or change field semantics without an ADR.

### 6.1 Document Contract (document-contract.md)
Root entity of the document lifecycle; a *logical* legal publication independent of file
format. Owns Metadata + Document Versions; references Vault, Organization, Permissions.
Lifecycle `Created → Active → Archived` (never physically deleted). Identifier is stable;
changing metadata ≠ new Document; a revised publication → new Document **Version**.
Key fields: `id, type (DocumentType), title, short_title, description, issuing_authority,
document_number, language, status (ACTIVE|ARCHIVED), visibility (PUBLIC|DEPARTMENT|PERSONAL),
vault_id, organization_id, created_at, updated_at, metadata, versions`.
Invariants: exactly one Vault, exactly one Organization, ≥1 Version, identifier never
changes, never stores parsed content / embeddings / chunks / AI-generated outputs.

### 6.2 Knowledge Tree Contract (knowledge-tree-contract.md)
Canonical, immutable output of the parsing pipeline. Consumed by Chunk Generator, Retrieval,
Citation Builder, Evaluation. One Root Node; a flat `nodes` registry allows traversal without
recursive walking; hierarchy remains authoritative.
- `KnowledgeTree`: id, document_version_id, parser_version, created_at, root (NodeReference),
  nodes (List<Node>), statistics, metadata.
- `Node`: id, type, title, text, parent (NodeReference|null), children (List<NodeReference>),
  order, page_start, page_end, source (SourceLocation), metadata.
- `SourceLocation`: page, line_start, line_end, bbox (BoundingBox|null).
- `NodeType`: Document | Chapter | Section | Article | Clause | Point | Paragraph |
  Appendix | Table | Figure | **Unknown** (graceful handling of non-standard internal regs).
- `TreeMetadata`: language, parser_confidence, ocr_confidence, warnings[], processing_time.
- `TreeStatistics`: node_count, depth, article_count, clause_count, appendix_count, page_count (informational only).

Invariants: exactly one Root; every non-root node has exactly one parent; globally unique
IDs; stable sibling order; every node references one source location; every char in the
original document belongs to exactly one node; the tree never contains chunks, embeddings,
or AI-generated text. No normalization/summarization/translation/AI correction of wording.

### 6.3 Retrieval Contract (retrieval-contract.md)
Boundary between Retrieval and Generation. **Transient** (request-lifetime only), not a
persistent business object. Generation must consume this contract instead of touching
vector databases, search engines, or storage directly.
- `RetrievalResult`: query_id, strategy, generated_at, query, evidence (List<Evidence>), metadata.
- `Evidence`: id, knowledge_node_id, document_id, document_version_id, score, rank, text,
  source_anchor, reason (informational only — Generation must never rely on it).
- `RetrievalMetadata`: strategy, latency_ms, candidate_count, returned_count, warnings[].
- `RetrievalStrategy`: Keyword | Semantic | Hybrid (BM25 / Vector / Hybrid / future methods
  are invisible to downstream — Generation consumes evidence, not search technology).

Invariants: every Evidence belongs to exactly one Knowledge Node; evidence text must match
the original parsed content; ranking is deterministic; evidence is immutable; an empty
evidence list is a valid result; retrieval never generates new knowledge and never modifies
source wording; retrieval never performs legal interpretation.

### 6.4 Answer Contract (answer-contract.md)
Final user-facing output; **presentation-oriented**; transient. Internal implementation
details (vector DB, embedding model, LLM provider, reranking algorithms) must never leak in.
- `Answer`: request_id, generated_at, status (SUCCESS | PARTIAL | NO_EVIDENCE | ERROR),
  response (Response), citations (List<Citation>), evidence (List<EvidenceReference>),
  confidence (Confidence), limitations (List<Limitation>), metadata (AnswerMetadata).
- `Response`: format (MARKDOWN), content.
- `Citation`: id, document_id, document_version_id, knowledge_node_id, source_anchor, label.
- `EvidenceReference`: evidence_id, usage (DIRECT | SUPPORTING | CONTEXT). References the
  Retrieval Contract's Evidence id; generation never duplicates evidence.
- `Confidence`: level (HIGH | MEDIUM | LOW), score, reason — **advisory only**, never legal certainty.
- `Limitation`: insufficient evidence / conflicting documents / ambiguous wording / incomplete
  upload / OCR uncertainty (improves transparency).
- `AnswerMetadata`: generation_model, generation_latency_ms, prompt_version,
  retrieval_strategy, token_usage (monitoring/debugging only).

Invariants: every factual claim supported by ≥1 Citation; never fabricated; evidence
references originate from the Retrieval Contract; generation never modifies citation
wording; the Answer Contract never creates new legal knowledge; exactly one Answer per
request; missing evidence is explicitly communicated.

### Governing design documents
- **System Prompt (design/system-prompt.md)** — model-independent Generation Service policy.
  Priority: Correctness → Traceability → Completeness → Clarity → Conciseness. Evidence
  hierarchy: Retrieved Evidence > Canonical References > Metadata > Background > Inference
  > Speculation. Quoting preserves original wording/punctuation. Citation granularity
  prefers Point > Clause > Article > Appendix > Document. Generation fails rather than
  fabricates. Never reveal hidden docs, unauthorized vault contents, or internal prompts.
  Conflict policy: present both sources, never silently resolve.
- **Benchmark Dataset Spec (design/benchmark-dataset-spec.md)** — hierarchy Suite → Dataset
  → Case → Evaluation Result. Dataset types: Unit, Component, Regression, Release,
  Production Replay, Research. Suggested minimum sizes: Parser 200, Retrieval 500,
  Generation 300, Citation 300, Regression 1000+, Release 500+. Datasets immutable once
  published; corrections require a new version. Gold standards reviewed by Domain Expert
  → Technical Reviewer → Approval. Every execution records Dataset/Prompt/Config/Model/Temperature/Seed/System versions for reproducibility.

### Milestone 0 — Foundation (Document Pipeline, canonical side)
Build the document processing pipeline and the canonical representation.
1. **Task 001 — Document Registry** (High/Medium). Entry point of ingestion; assigns stable
   Document ID; stores metadata, processing status, versions, relationships, vault ownership;
   duplicate detection by checksum; lifecycle state machine. Produces Document Contract.
2. **Task 002 — Upload Service** (High/Medium). File transfer + storage; checksum; corruption
   detection; forwards metadata to Registry. Does NOT register identity itself.
3. **Task 003 — OCR Service** (High/High). Detects if OCR is needed, extracts text,
   preserves reading order and page/line boundaries, produces confidence scores, flags
   low-confidence documents for manual review. Never modifies originals.
4. **Task 004 — Parser** (Critical/Very High). Converts OCR output into the structured
   Knowledge Tree; detects Chapters/Sections/Articles/Clauses/Points; preserves wording,
   numbering, order; records source locations; emits parser diagnostics. Only component
   allowed to construct a Knowledge Tree (candidate — see F3).
5. **Task 005 — Knowledge Tree Builder** (Critical/High). Converts parser output into the
   validated Knowledge Tree Contract: builds nodes, parent-child links, Node IDs, canonical
   references, paths, depth; preserves ordering; validates tree integrity. Consumes parser
   output only — does not parse raw text.

### Milestone 1 — Search (Retrieval, derived/disposable side)
6. **Task 006 — Chunking** (Critical/High). Structure-aware — Knowledge Tree boundaries
   always take priority over token limits (KT → Legal Meaning → Token Size). Source mapping
   preserved; oversized chunks split Article→Clause→Point→Sentence; undersized chunks merge
   only with same-parent siblings (never across Articles).
7. **Task 007 — Embedding Service** (High/Medium). Renders chunks → embedding text → vectors;
   embedding versioning; re-embedding triggers = KT update / chunk change / model change /
   config change. Re-embedding does not interrupt retrieval.
8. **Task 008 — Vector Index** (High/Medium). Stores + searches embedding vectors; metadata
   filtering (Vault/Document/Type/Status/Language/KT-Version/Chunk-Type); version-aware
   indexing; eventually consistent (KT authoritative); index corruption never affects the KT.
9. **Task 009 — Retrieval Service** (Critical/Very High). Hybrid (keyword + semantic) + ranking
   + filtering + vault scoping → returns the Retrieval Contract. Candidate collection →
   re-ranking → context expansion → deduplication. Never generates answers.
10. **Task 010 — Reranker** (High/High). Refines candidates and produces the final evidence
    set for Generation — **precision after retrieval's recall**. Never generates answers;
    never retrieves new documents; respects vault budget and context-budget constraints.

### Milestone 2 — Answering (Generation)
11. **Task 011 — Generation Service** (Critical/High). Converts retrieved evidence into a
    structured Answer Contract per the System Prompt policy. Explains, never invents; never
    retrieves additional evidence; never reads originals. Reports confidence from
    evidence quality/coverage, not model confidence alone.
12. **Task 012 — Citation Builder** (Critical/High). Constructs, validates and attaches
    citations; claim detection → evidence mapping → citation resolution → validation;
    detects unsupported claims (triggers generation retry). References the Knowledge Tree.

### Milestone 3 — Knowledge Platform (user-facing MVP surface)
13. **Task 013 — Vault Service** (Critical/High). Primary authorization layer; vault
    isolation, department separation, personal vaults, permission checks. Vault types:
    Common / Department / Project / Personal. Depends on Tasks 001–012.
14. **Task 014 — Platform API** (Critical/High). The only public entry point; stable,
    versioned (/v1), RESTful, JSON, contract-driven, stateless, idempotent where applicable.
    Domains: Auth, Vault, Document, Upload, Search, Q&A, Admin, Health. Business logic stays in internal services.
15. **Task 015 — Web UI** (High/High). Primary interaction surface — no business logic; all
    operations via the Platform API. Knowledge-discovery UX over conversational AI;
    transparency over automation. Citation viewer, document viewer, upload pipeline monitor.

### Milestone 4 — Production (selective for MVP)
16. **Task 016 — Observability** (High/Medium). Logs/Metrics/Traces/Evaluation pillars;
    structured logs, health endpoints, dashboards, alerts, audit trail (immutable). Consumes
    events from all stages; never affects business logic. Telemetry should be async.
17. **Task 017 — Evaluation Platform** (Critical/High). Objective measurement per the
    Benchmark Dataset Spec; Pipeline = Benchmark Suite → Dataset → Execution → Metric
    Collection → Analysis → Comparison → Report. Regression detection vs configurable
    baselines; independent of production traffic; never modifies production data.
18. **Task 018 — Release Checklist** (Critical/Low). Standardized release validation —
    functional/quality/operational/security/observability/documentation gates; rollback plan;
    post-release verification; release artifacts. No production deployment bypasses it.

### Future (NOT MVP; do not implement unless explicitly directed)
- **Milestone 5 — Enterprise**: RBAC, SSO, multi-organization, document lifecycle
  management, workflow automation, notifications, audit portal, reporting, API tokens,
  SDK, MCP server.
- **Milestone 6 — Intelligence** (research): query planner, adaptive retrieval,
  learning-to-rank, Knowledge Graph retrieval, cross-document reasoning, agent-assisted
  research, automatic summaries, recommendation engine, semantic navigation.

## 9. Engineering & Workflow Discipline (binding)

From `developer-guide.md` + `docs/`.

**Documentation hierarchy (when conflicts exist, higher wins):**
ADR → Contracts → Architecture → Examples → Implementation. Implementation must never
become the source of truth. Code follows documentation.

**Per-task workflow (developer-guide.md + docs/01-implement-task.md):**
Read the task → read the related ADR → read the related contract → read the related example →
implement → run tests → validate contracts → return results (completed work / changed files /
design decisions / risks / remaining work) → **wait for the next instruction**. Only the
requested task is implemented; do not auto-advance.

**Definition of Done** (developer-guide.md): implementation finished ∧ contracts remain valid
∧ examples pass ∧ tests pass ∧ documentation updated ∧ code reviewed.

**Prohibitions:** never invent contracts, silently change architecture, bypass module
boundaries, hardcode business rules, skip validation, or modify specs/contracts/examples
without an ADR. Errors must be Observable, Recoverable, Traceable — silent failures are
unacceptable.

**Versioning:** Parser, Knowledge Tree, Embedding, Contracts, and Examples all versioned
independently. Contract modification requires ADR → Contract Update → Examples Update → Implementation Update.

## 12. Specification Consistency Report

Cross-spec review produced the following findings. Per `docs/02-review.md` +
`docs/00-project-init.md` (Phase 3 — "produce a report. Do not invent fixes"), these are
**reported, not fixed**. None block starting Task 001, but several must be reconciled before
the relevant task's example/example-validation gate passes.

### F1 — Dual project name (naming, not semantic)
- README.md / contracts / this context doc call it **"Legal Knowledge Platform"**.
- scope.md / constraints.md / capability-map.md / glossary.md / domain-model.md / architecture.md /
  deployment-view.md / module-specifications.md / processing-pipeline.md / ADRs / most task headers call
  the concrete product **"Banking Legal Platform"**.
- These refer to the same project (generic system vs. concrete banking-regulation instance).
- **Recommendation:** align on one canonical name; treat the other as an alias in the glossary.

### F2 — Minor priority-ordering variance across documents (same idea, different orderings)
- `constraints.md` (canonical NFR priority): Accuracy → Traceability → Reliability → Maintainability → Performance.
- `scope.md`: Accuracy → Explainability → Maintainability → Modularity ("Performance secondary to correctness").
- `developer-guide.md`: Accuracy → Correct Citation → Maintainability → Performance.
- `design/system-prompt.md` (Generation-specific): Correctness → Traceability → Completeness → Clarity → Conciseness.
- `roadmap.md`: Correctness → Traceability → Maintainability → Performance → User Experience.
- **Recommendation:** treat `constraints.md` as the system-wide canonical priority and the
  others as scoped refinements (system-prompt = generation-specific; roadmap adds UX). Worth a one-line note in the glossary.

### F3 — Parser vs. Knowledge Tree Builder ownership seam
- `tasks/004-parser.md`: "The Parser is the only component allowed to construct a Knowledge Tree."
- `tasks/005-knowledge-tree-builder.md`: A separate task that "transforms parsed structural elements
  into a validated Knowledge Tree" and "does not perform parsing."
- `module-specifications.md`: lists a single **Ingestion** module producing the KT Contract; no separate
  Builder module and no separate "parse structure" sub-module.
- **Interpretation that resolves it:** Parser constructs the candidate structural output; Builder
  validates/normalizes it into the published Knowledge Tree Contract. The word "construct" in 004
  could be read as "extract the structure" — but the contract's immutability invariant means the KT
  only exists once it's validated/persisted by the Knowledge layer.
- **Recommendation:** clarify in 004 whether "construct" means "produce the candidate structure"
  (Builder then finalizes) or whether the two tasks should be re-scoped. Low risk; resolve before 005.

### F4 — Reranker: peer module vs. sub-step of Retrieval (the only structural ambiguity)
- `tasks/009-retrieval.md` includes "Re-ranking" as an internal processing step.
- `tasks/010-reranker.md` is a distinct task ("refines retrieval candidates and produces the final
  evidence set that will be consumed by the Generation Service") with dependency 009→010.
- `module-specifications.md` does **not** list a Reranker module; the module chain goes
  `… → Retrieval → Generation → Citation → Client`. Reranking is mentioned only as a future
  Extension Point in `retrieval-contract.md`.
- `tasks/017-evaluation.md` evaluates "Ranking" as a separate component.
- **Recommendation:** decide and document whether Reranker is (a) a sub-step of Retrieval, or
  (b) a peer module. The tasks + dependency graph + evaluation scope all treat it as a peer; if so,
  `module-specifications.md` should add it. Either way, update 009's "Re-ranking" step wording to
  "candidate collection hands off to Reranker." Resolve before Milestone 1 finishes.

### F5 — Example JSON does not match the canonical Contracts (will fail example-validation gate)
The developer-guide says "Examples are executable documentation… Examples are not optional" and the
Definition of Done requires "examples pass." Multiple field/shape mismatches exist:

- **Document example vs Document Contract:** example uses `document_id` (contract: `id`),
  `document_type` (contract: `type`), adds `effective_date / expiry_date / source{...} /
  processing{status,parser_version,knowledge_tree_version} / relationships{...} / tags[]` that the
  contract does not define; example `vault.visibility = "SHARED"` while contract `visibility` enum
  is `PUBLIC | DEPARTMENT | PERSONAL` (direct contract violation — see F6).

- **Knowledge-tree example vs Knowledge Tree Contract:** node uses `node_id` (contract: `id`),
  `parent_id` (contract: `parent` NodeReference), `content` (contract: `text`), `number`
  (not in contract Node), `source.start_line / end_line` (contract: `line_start / line_end`),
  `children[]` (contract: `List<NodeReference>`); the contract's `order / page_start / page_end /
  metadata` Node fields are absent from the example.

- **Retrieval example vs Retrieval Contract:** example nests `query{original, normalized,
  language, vault_scope}`, `strategy{type, keyword_search, semantic_search, reranking}`,
  `summary{total_candidates, retrieved, latency_ms}`, and `evidence[].document{id,title,
  document_number,status} + node{node_id,type,canonical_reference,path} + content + match{...}`.
  Contract defines flat `RetrievalResult{query_id, strategy, generated_at, query, evidence[], metadata}`
  and `Evidence{id, knowledge_node_id, document_id, document_version_id, score, rank, text,
  source_anchor, reason}`. Field names and nesting differ materially.

- **Answer example vs Answer Contract:** example uses `answer_id` (contract: `request_id`),
  `query{query_id, original}` (not in contract), `answer{summary, details[]}` (contract:
  `response{format, content}`), `citations[].reference{canonical_reference, node_id}` (contract:
  `Citation{id, document_id, document_version_id, knowledge_node_id, source_anchor, label}`),
  `evidence[].evidence_id, rank` (contract: `EvidenceReference{evidence_id, usage}` — missing the
  `usage` enum), `confidence{level, score}` (contract: adds `reason`), `generation{model,
  generated_at, latency_ms}` (contract `AnswerMetadata{generation_model, generation_latency_ms,
  prompt_version, retrieval_strategy, token_usage}`). `generated_at` at top level is missing.

- **Recommendation:** before the example-validation gate of any task (001, 004/005, 009/010,
  011/012), the examples must be reconciled to the contracts OR the contracts extended via ADR.
  The examples currently encode a richer, implementation-leaning schema than the contracts specify.

### F6 — Vault taxonomy vs `visibility` enum mismatch (contract-level)
- `document-contract.md` `visibility`: `PUBLIC | DEPARTMENT | PERSONAL` (3 values).
- `domain-model.md` Vault examples: Personal / Department / **Shared**.
- `scope.md` + `constraints.md` (SC-003/004): Personal + Department only.
- `tasks/013-vault-service.md` Vault types: **Common / Department / Project / Personal** (4 types).
- `document-example.json`: `"visibility": "SHARED"` — a value **not in the contract enum**.
- **Recommendation:** reconcile vault taxonomy (number of types and names) and align the
  `visibility` field so it can encode Common/Project vaults. The example's `"SHARED"` is a hard
  contract violation. Resolve before tasks 001 (visibility field) and 013 (vault model).

### F7 — `"status"` field name collision: Document lifecycle vs. Processing lifecycle
- `document-contract.md` Document `status`: `ACTIVE | ARCHIVED` (lifecycle Created→Active→Archived).
- `document-example.json` carries both top-level `status: "ACTIVE"` (lifecycle) **and**
  `processing.status: "UPLOADED"` (processing state).
- `deployment-view.md` runtime states: Uploaded → Queued → Processing → Indexing → Ready →
  Archived → Reprocessing.
- `tasks/001-document-registry.md` lists a finer-grained state machine: Uploaded → OCR_PENDING →
  OCR_RUNNING → OCR_COMPLETED → PARSING_PENDING → PARSING_RUNNING → READY → Archived → Failed.
- **Issue:** two orthogonal state machines share the `"status"` name (one on Document, one on
  processing). Per ADR-003 / `constraints.md` DC-003, **metadata must stay independent of document
  content** — processing state is derived/mutable; document lifecycle is canonical.
- **Recommendation:** clearly separate fields (e.g. `document_status` vs `processing_status`) so the
  two cannot be conflated. The `processing.status` sub-object in the example is the right instinct;
  make the contract explicit about it.

### F8 — `"effective_date" / "expiry_date"` exists in examples but not the Document Contract
- `constraints.md` SC/DC and `glossary.md` Metadata explicitly list Effective Date, Issue Date,
  Expiration Date; `tasks/001` stores "legal status".
- `document-contract.md` has a `Metadata` block (described in prose, "Issue Date / Effective Date
  / Expiration Date / Tags / Keywords may evolve without changing document identity") but the
  contract YAML only declares `metadata: Metadata` without enumerating those sub-fields.
- The example carries `effective_date` / `expiry_date` as Document-level fields.
- **Recommendation:** decide whether Effective/Expiration dates are Document-level fields or live
  inside `metadata`; then state it in the contract. Resolve before 001.

### F9 — Citation granularity preference differs between system-prompt and citation-builder
- `design/system-prompt.md`: granularity prefers **Point → Clause → Article → Appendix → Document**.
- `tasks/012-citation-builder.md`: granularity prefers **Clause → Point → Sentence → Article**.
- "Smallest meaningful citation" is the agreed principle, but the exact ordering (and the
  inclusion of "Sentence") differs.
- **Recommendation:** reconcile ordering; consider "Sentence" an allowed fallback only when no
  Point/Clause exists.

### F10 — Release checklist references a "Query Planner" not in the MVP
- `tasks/018-release-checklist.md` Retrieval Pipeline gate: "☐ Query Planner operational".
- No Query Planner task/module exists in MVP; per `tasks/019-roadmap.md` a Query Planner is a
  **Milestone 6 (Intelligence / research)** feature.
- **Recommendation:** remove the Query Planner checklist line for the MVP release, or mark it
  "N/A for v1 (post-MVP)". Resolve before 018 is exercised.

### F11 — Minor: example `generation.model = "gpt-5.5"` and field names vs AnswerMetadata
- `answer-example.json`: `generation{model, generated_at, latency_ms}`.
- `answer-contract.md` AnswerMetadata: `generation_model, generation_latency_ms, prompt_version,
  retrieval_strategy, token_usage` (no `generated_at`; that lives at Answer top level).
- Also the example lists no `prompt_version / retrieval_strategy / token_usage`.
- Covered under F5; called out because it is the most concrete AnswerContract drift.

## 13. Operational Reference — Quick Decisions Table

| Area | Decision | Source |
|---|---|---|
| Canonical representation | Knowledge Tree (immutable). All downstream artifacts derive from it. No component reads sources directly. | ADR-001 |
| Generation model | Evidence-first: Generation consumes only the Retrieval Contract; never retrieves, never reads PDFs, never builds answers from pretrained knowledge. | ADR-002 |
| Persistence model | Canonical data persists + is backed up + versioned; derived artifacts (chunks/embeddings/indexes/caches) are disposable and rebuildable. KT is sufficient to reconstruct the entire retrieval infrastructure. | ADR-003 |
| Failure behavior | Failures stop the pipeline early (no silent failure). Empty evidence → `status = NO_EVIDENCE`. The platform abstains rather than fabricates. | constraints.md, processing-pipeline.md |
| Retrieval strategy | Hybrid (keyword + semantic) with metadata filters, default. Retrieval determines *what is relevant*; Generation determines *how to communicate it*. | architecture.md, ADR-002 |
| Primary language | Vietnamese (vi); corpus = Decisions/Circulars/Decrees/Laws/internal banking regulations. | vision/README/examples |
| Authorization granularity | Vault-scoped: Common / Department / Project / Personal. Permission filtering occurs **before** retrieval. No module bypasses Vault validation. | tasks/013, architecture.md, constraints.md SC-001..004 |
| Documentation hierarchy | ADR > Contracts > Architecture > Examples > Implementation. Implementation is never the source of truth. | developer-guide.md |
| Task concurrency | One implementation task active at a time; wait for the next instruction. | README, docs/01-implement-task.md |
